# PRD: 庫存管理系統（倉管與採購端 · 教學示範版）

*把「東西在哪、還剩多少、該補多少」收進同一本帳的進銷存後台。聚焦倉管與採購兩端，銷售只做最小可用。*

## 0. 文件目的

本文件是「庫存管理系統」課程專題的產品需求文件（PRD），供授課教師、學生（開發者）與評審者使用：說明這套系統要解決什麼問題、給誰用、有哪些能力、v1 做到哪裡為止。文件以第 3 節術語表為用詞基準，功能以功能群組組織、需求以全域編號的 FR 條列，推論之處以 `[ASSUMPTION]` 標記並集中索引於第 11 節。

本 PRD 只描述「系統要做什麼能力」，不描述「怎麼做」。技術選型、資料表草案、架構分層、環境前置步驟與被排除方案的理由收在同目錄的 `addendum.md`；領域參考（60 個來源）收在 `research-landscape.md`；本機資料庫環境收在專案根目錄的 `資料庫使用手冊.md`（該手冊含本機練習用的明文密碼與連線字串，尚未排除於版本控制之外，處理方式見 `addendum.md` §1.10）。決策來源與未決事項記錄在 `.memlog.md`。

**課程簡報來源：** `庫存管理課題.pptx`（位於使用者下載資料夾，未納入本專案目錄；本文提及的簡報頁碼以此檔為準）。

**範圍取向。** 本系統深度集中在**倉管端與採購端**；銷售端只做「能建立銷貨單並扣減庫存」的最小可用。v1 全部 23 條功能需求都必須跑得動，沒有「選做」層——理由與代價見第 7 節。

## 1. 願景

這是一套給中小型貿易／製造商的**庫存與補貨後台**：把「商品在哪個庫位、還剩多少、批次是什麼、最後是誰動的」與「哪個商品快見底了、該跟誰買、買多少」這兩條最容易出事的主線，收斂到同一本帳上。對倉管人員而言，它取代的是白板、便當紙與 Excel；對採購而言，它取代的是對著舊對帳表猜數量。

這套系統同時是**教學產物**：它被設計成能講清楚分層架構（MVVM 與 MVC 的取捨）、單一庫存異動引擎的設計、關聯式資料庫建模、權限分層與稽核軌跡這些看得見的工程命題。因此「可被示範與可被檢驗」和「功能完整」同等重要——每一條需求都應該能在一堂課內被啟動、被驗證、被檢視。

**本 PRD 押注的命題**（後續所有取捨都以此為準，硬性約束見第 6 節）：對中小型貿易商而言，庫存管理的難點不在「把數字記下來」，而在「數字被動過之後還能不能說清楚」。因此本系統把「任何庫存數量變動只能由單據產生、必須留下是誰動的」放在功能豐富度之前——寧可少做模組，不可放寬這條規則。

## 2. 目標使用者

### 2.1 Jobs To Be Done

- **倉管人員**：「我要用最快的方式找到東西在哪、還剩多少，並且任何異動都留下是誰動的紀錄，讓我不用在開會時解釋帳實不符。」
- **倉管人員**：「收貨、領用、移位這三件天天做的事，我要用最少步驟完成，最好是掃條碼就完成。」
- **採購人員**：「我要一眼看出哪些商品低於安全水位、該補多少貨、跟哪個供應商買比較划算。」
- **主管**：「我要能核准盤點差異與庫存調整，並且隨時查得到這筆是誰動的、依哪張單據。」
- **銷售人員（最小需求）**：「我要能把賣掉的商品記成一張單，讓庫存數字自動扣減，不用回頭請倉管幫我改數字。」
- **授課教師（次要使用者）**：「我需要一套能示範完整業務流程、資料可重置、架構能被學生讀懂的系統。」

### 2.2 非使用者 (v1)

- 消費者／客戶自助入口（不提供線上訂購或查詢）
- 外部供應商與承攬商的自助協作入口
- **會計人員（簡報第 10 頁列出的第四種職能）** — v1 不設會計角色、不做會計分錄與成本結轉，只提供採購單價與進貨金額的查詢
- 決策者對「毛利分析、定價建議、呆滯資金占用」的需求（見第 7 節）
- 生產製造的 BOM／MRP 排程與工單

### 2.3 關鍵使用者旅程

**UJ-1. 倉管小陳掃條碼完成收貨，40 箱飲料 3 分鐘入庫。**
- **人物與情境**：倉管人員小陳，早上 8 點在收貨區，廠商送來今天到貨的 40 箱飲料，櫃上有廠商的採購單。
- **進入狀態**：已登入，使用桌上型電腦與 USB 掃描器。
- **路徑**：小陳開啟「進貨」→ 掃描採購單號帶出待收品項 → 逐箱掃商品條碼，系統自動帶出品名、採購單價與建議庫位 → 輸入數量 40 → 指定庫位 A-01-03 → 送出。
- **高光**：送出後畫面立即顯示「A-01-03 已入庫 40 箱，可用庫存同步更新」，並自動產生進貨單號與庫存異動紀錄，該批次的批次數量更新為 40。
- **收尾**：小陳回到待收清單，該採購單顯示「已收 40／40，待收 0」。
- **邊界情況**：若掃到的商品不在該採購單上，系統擋下並提示改用「無單據入庫」並要求說明原因。

**UJ-2. 倉管小陳用盤點找出那 2 箱不見的飲料。**
- **人物與情境**：倉管人員小陳，月底對飲料類做循環盤點。
- **進入狀態**：已登入，開啟「盤點」功能，選擇範圍（庫位／商品類別／商品）。
- **路徑**：系統凍結該範圍的庫存異動並帶出帳面數量 → 小陳逐項掃描條碼輸入實盤數量 → 提交盤點結果。
- **高光**：提交後系統產出差異清單：飲料 2 項盤虧共 2 箱，盤點差異率 0.4%，畫面標示需主管核准。
- **收尾**：主管核准後，系統自動產生庫存調整並記錄異動原因為「盤虧」。
- **邊界情況**：盤點期間若有其他單據要異動同一範圍的商品，系統阻擋並提示盤點單號，需先中止盤點或由主管放行。

**UJ-3. 採購小美從低於水位清單直接生出採購單。**
- **人物與情境**：採購人員小美，每週一固定檢視補貨。
- **進入狀態**：已登入，開啟「補貨建議」清單。
- **路徑**：清單列出低於安全水位的 6 項商品，標示現存數量、安全水位、建議採購量與最低供應商報價 → 小美勾選 4 項 → 帶入供應商報價產生採購單草稿 → 送出待核准。
- **高光**：採購單顯示總價與預估交期，小美可調整數量後直接送出。
- **收尾**：採購單核准後，倉管在進貨畫面可看到這張待收採購單。

**UJ-4. 倉管小陳領用 3 箱膠帶並註明用途。**
- **人物與情境**：倉管人員小陳，維修班領用膠帶 3 箱，非銷售用途。
- **進入狀態**：已登入，開啟「領用出庫」。
- **路徑**：掃描或搜尋商品 → 選擇庫位與數量 → 用途選「內部損耗」並補註說明 → 送出。
- **高光**：畫面顯示領用後的剩餘可用庫存，並產生一筆帶用途的庫存異動。
- **收尾**：小陳可在庫存異動查詢中看到這筆領用，依用途篩選出所有非銷貨出庫。
- **邊界情況**：若可用庫存不足，系統拒絕並顯示目前可用庫存與所在庫位。

**UJ-5. 銷售小李把賣掉的商品記成一張單。**
- **人物與情境**：銷售人員小李，客戶現場買走 2 項商品。
- **進入狀態**：已登入桌面版後台，客戶在店內等待結帳。
- **路徑**：小李輸入商品編號查即時可用庫存 → 建立銷貨單加入 2 項商品、填數量與單價 → 送出。
- **高光**：畫面顯示成交金額，送出後對應庫存立刻扣減，小李不需要另外通知倉管。
- **收尾**：銷貨單進入單據流轉，可作廢重開；作廢時庫存自動回滾。
- **邊界情況**：若可用庫存不足，系統在送出前擋下並顯示各庫位可用庫存。

## 3. 術語表

*本文件其餘章節一律使用下列詞彙，不使用同義詞。*

- **商品** — 以商品編號識別、可被採購與存放的最小庫存管理單位。
- **商品編號** — 系統自動產生的商品識別碼（格式 `P-` + 6 碼遞增），唯一且建立後不可變更。（台灣慣用「品號」）
- **商品條碼** — 商品主檔上的條碼欄位，一個商品最多對應一條且全系統唯一；掃描器輸入即以此比對。
- **商品類別** — 商品的分類層級，用於彙總報表、安全水位預設與盤點範圍挑選。
- **包裝換算** — 商品的基本單位與包裝單位的換算關係（例如 1 箱 = 12 罐），每個商品一組。
- **批號** — 同一商品下唯一的批次識別碼，用於追溯商品來源；同一批號可分批進貨，數量累計。
- **批次數量** — 某批號目前入庫的累計數量。
- **效期** — 商品的最後可使用日期，選填。
- **倉庫** — 實體存放庫存的場所。v1 只有一個倉庫。
- **庫位** — 倉庫內的儲存位置，可設定凍結狀態。
- **現存數量** — 某商品在某庫位的實體數量。
- **可用庫存** — 可即時動用的庫存數量。v1 沒有任何「預留／保留」機制（沒有先扣後核的單據），因此**可用庫存 = 現存數量**；未來若加入訂單預留，需另行擴充資料模型。
- **庫存異動** — 任何造成庫存數量增減的動作，記錄於不可變的結存明細。
- **結存明細** — 記錄每一筆庫存異動的明細表，僅能追加，不可修改或刪除。
- **進貨單** — 商品實際入庫的單據，產生庫存異動。
- **銷貨單** — 商品賣出的單據，產生庫存異動。
- **盤點單** — 記錄特定範圍的實盤數量並與帳面數量比較的單據。
- **盤點範圍** — 盤點單所涵蓋的庫位、商品類別或商品組合，至少指定一項。
- **盤盈／盤虧** — 實盤數量高於／低於帳面數量的差異。
- **差異率** — Σ|實盤 − 帳面| ÷ Σ帳面，顯示至小數 2 位。
- **帳實相符率** — 本次盤點中，實盤數量與帳面數量相符的品項比例，為整張盤點單的一個整體指標。
- **庫存調整** — 經核准後直接修正帳面數量的單據。
- **領用** — 取用庫存並註明用途，用途不含銷貨（銷貨一律走銷貨單）。
- **移位** — 在同一倉庫內更換庫位，不影響總量。
- **用途** — 領用原因，分為客戶寄貨、內部損耗、其他。
- **安全水位** — 商品低於此數量即視為需要補貨的門檻，可依商品或商品類別設定。
- **補貨倍數** — 計算建議採購量時，安全水位要乘上的倍數。
- **建議採購量** — 依安全水位與補貨倍數扣除可用庫存後算出的建議下單量。
- **供應商** — 提供商品的廠商或貿易商。
- **供應商報價** — 特定商品由特定供應商提供的單價、起訂量與交期。
- **採購單** — 向供應商提出請購的單據，含明細、數量、單價與預估交期。
- **採購批次流水號** — 採購單核准時自動指派的單號，格式 `PO-YYYYMMDD-序號`，即採購單的單號。
- **採購單價** — 商品進貨時的單筆成交單價。
- **批次進貨單價** — 進貨時歸屬某批號的單筆單價，v1 與採購單價同值。
- **帶入日期** — 採購單被核准的日期（`PO-YYYYMMDD` 中的日期部分）。
- **單據** — 採購單、進貨單、銷貨單、盤點單、庫存調整的統稱。
- **送單／核准／作廢重開** — 單據流程用語；已送單或已核准的單據不可修改，只能作廢後重開新單。
- **角色** — 賦予一組功能權限的職能集合，共三種：倉管、採購、主管（銷售功能由主管兼任）。
- **權限** — 可執行的功能與可見的欄位範圍。
- **稽核軌跡** — 不可竄改的操作紀錄，含操作者、時點、物件與異動前後值。
- **稽核紀錄** — 稽核軌跡中的一筆紀錄。
- **種子資料** — 供授課示範與測試使用的初始資料。

## 4. 功能需求

### 4.1 帳號、角色與權限

**描述：** 系統以帳號 + 角色運作，角色決定可用的功能選單；採購單價對倉管遮蔽——台灣進銷存慣例是「倉管管量不管價」。[ASSUMPTION: 權限模型採固定角色（倉管／採購／主管），不建自訂授權規則引擎]

**功能需求：**

#### FR-1: 帳號登入與登出
[使用者] 可以 以帳號與密碼登入系統並登出。

**可測試結果：**
- 帳號或密碼錯誤時不透露帳號是否存在，錯誤訊息一致。
- 閒置逾時（預設 30 分鐘）自動登出，未儲存的表單內容提示保存；API 存取權杖的有效期與此一致。
- 登入後畫面只顯示該角色被授權的功能選單。

#### FR-2: 角色指派與功能權限
[主管] 可以 將帳號指派至倉管、採購或主管角色。

**可測試結果：**
- 採購帳號看不到盤點建立入口；倉管帳號看不到採購單核准。
- 新指派角色後，重新登入即生效。
- 角色權限變更記錄於稽核軌跡。

#### FR-3: 採購單價欄位遮蔽
[系統] 可以 依角色權限遮蔽採購單價與批次進貨單價欄位。

**可測試結果：**
- 倉管帳號在進貨單與庫存查詢看不到採購單價，API 回應亦不含該欄位。
- 採購與主管角色可見。
- 遮蔽在 API 序列化層完成，不依賴前端隱藏；同一支 API 對不同角色回傳不同欄位。

### 4.2 商品與供應商主檔

**描述：** 商品是全系統的核心主檔，帶有編號、條碼、類別、包裝換算、批號與採購單價；供應商是商品條碼之外的第二條識別路徑。[ASSUMPTION: 條碼輸入為主要商品識別方式，仍保留以商品編號或名稱手動挑選的退路（無條碼商品仍可建檔）]

**功能需求：**

#### FR-4: 商品建檔
[倉管或採購人員] 可以 建立商品，輸入名稱、商品條碼、商品類別、單位、包裝換算與採購單價；商品編號由系統自動產生。

**可測試結果：**
- 商品編號唯一且自動遞增，建立後不可修改。
- 商品條碼全系統唯一，同一條碼不可指向兩個商品。
- 同一商品類別下名稱重複時提示確認（不阻擋，但需留下確認紀錄）。
- 包裝換算換算後數量四捨五入至小數 3 位；庫存數量一律以基本單位儲存，換算只在輸入與顯示層發生。

#### FR-5: 批次與效期
[倉管人員] 可以 在商品主檔指定是否啟用批次管理，並在進貨時輸入批號與效期。

**可測試結果：**
- 啟用批次管理的商品，進貨時必須輸入批號；未啟用的商品進貨時不顯示批號欄位。
- 以掃描器輸入的條碼若無對應商品，系統拒絕並提示改用手動挑選。
- 同一商品下批號唯一；同一批號可分批進貨，系統將數量累計為該批次的批次數量。
- 效期為選填。

#### FR-6: 商品停用
[主管] 可以 停用不再使用的商品，且停用商品不可用於新單據。

**可測試結果：**
- 停用商品不出現在新進貨、新銷貨的商品挑選清單。
- 歷史單據仍可顯示該商品資訊。
- 仍有庫存的商品停用時，系統提示需先移出庫存或撤銷停用。

#### FR-7: 供應商主檔與商品報價
[採購人員] 可以 建立、修改與停用供應商，並登錄商品的供應商報價。

**可測試結果：**
- 供應商欄位含統編、公司名稱、聯絡人、電話；統編格式驗證為 8 碼數字，與既有供應商不可重複。
- 缺少公司名稱時無法儲存；電話支援多筆並做格式驗證。
- 同一商品可關聯多個供應商並各有多筆報價（單價、起訂量、交期）。
- 補貨建議清單對每項商品顯示最低報價與對應供應商；報價可設定生效期間，過期報價不帶入採購單。

### 4.3 倉庫與庫位

**描述：** v1 只有一個倉庫，庫位是庫存數量的最小歸屬單位，可凍結。

**功能需求：**

#### FR-8: 倉庫與庫位主檔
[主管] 可以 維護倉庫與其下的庫位結構，並設定庫位的凍結狀態。

**可測試結果：**
- 庫位以階層呈現，父層可設為彙總層（不直接存放）。
- 凍結庫位不可入貨、出貨或移入。
- 已被使用過的庫位不可刪除，只能停用。

### 4.4 庫存異動

**描述：** 所有庫存數量變化都必須經由同一套領域規則產生，並寫入不可變的結存明細；進貨、領用、移位共用同一套異動引擎。

**功能需求：**

#### FR-9: 進貨單
[倉管人員] 可以 建立進貨單，對應採購單或選擇無單據入庫，輸入品項、數量、批號、效期與庫位。送出後立即產生庫存異動。

**可測試結果：**
- 進貨單可由待收採購單帶入品項，也可自行建立；對應的採購單必須為已核准狀態才能收貨。
- 進貨單送出即寫入庫存異動，且不可編輯（更正須以庫存調整處理）。
- 同一採購單可分批收貨，已收量累計不得超過訂購量（超收需主管放行，放行者與原因須寫入單據）。
- 進貨日期記錄於進貨單；商品層的「最新採購日期」由進貨單推導顯示，不另存欄位。
- 掃到的商品不在該採購單上時，系統擋下並提示改用「無單據入庫」並要求說明原因。

#### FR-10: 無單據入庫
[倉管人員] 可以 在沒有採購單時登錄入庫，必須選擇原因。

**可測試結果：**
- 原因為必填，且列入稽核軌跡。
- 該類進貨在採購金額統計中可被篩選區分。
- 無單據入庫不計入任何採購單的已收量。

#### FR-11: 領用出庫
[倉管或主管] 可以 領用庫存並指定用途（客戶寄貨、內部損耗、其他）。

**可測試結果：**
- 領用數量不得超過可用庫存，超出時顯示目前可用庫存與所在庫位。
- 每筆領用必須有用途與操作者。
- 用途不包含「銷貨」；銷貨一律以銷貨單（FR-18）記錄，避免同一批出庫有兩條記帳路徑。
- 領用產生庫存異動並更新可用庫存。

#### FR-12: 庫存移位
[倉管人員] 可以 在同一倉庫內將商品移至另一庫位。

**可測試結果：**
- 移位不改變該倉庫的總量，只改變庫位分布。
- 移位以**兩筆**結存明細記錄（一筆在來源庫位減、一筆在目標庫位增），因此各庫位分別加總皆可還原，庫存總量自然守恆。
- 目標庫位處於凍結狀態時拒絕移位。
- 移位記錄於庫存異動，異動類型為移位。

#### FR-13: 庫存異動明細與查詢
[有權限的使用者] 可以 依商品、庫位、批號、日期、單據類型與操作者查詢庫存異動。

**可測試結果：**
- 每一筆庫存數量變化都對應到唯一一筆結存明細；結存明細的序號由應用層指派、單調遞增且不重複（交易回滾可能造成跳號，不影響正確性）。
- 每筆異動顯示異動前後數量、批次、操作者與來源單據號。
- 異動紀錄不可刪除，無任何介面或 API 提供刪除功能。

### 4.5 盤點

**描述：** 盤點是「帳實相符」唯一的資料來源：凍結範圍內異動，產出差異並經核准後轉為庫存調整。

**功能需求：**

#### FR-14: 建立盤點單與盤盈盤虧
[倉管人員] 可以 依庫位、商品類別或商品建立盤點單，系統帶出帳面數量並在提交時比對產生盤盈／盤虧。

**可測試結果：**
- 盤點範圍至少需指定一項條件。
- 盤點單可中斷後繼續，已填實盤數量不遺失。
- 差異率 = Σ|實盤 − 帳面| ÷ Σ帳面，顯示至小數 2 位。
- 差異清單顯示盤盈、盤虧數量與差異率；帳實相符率為整張盤點單的整體指標，另列於盤點結果摘要。
- 提交後盤點結果不可修改，須作廢重開。

#### FR-15: 盤點凍結、差異核准與庫存調整
[系統] 可以 在盤點期間凍結盤點範圍內的庫存異動；[主管] 可以 核准盤點差異並自動轉為庫存調整；[倉管人員] 可以 提交手動庫存調整申請（數量、原因）。

**可測試結果：**
- 凍結期間對範圍內商品的進貨、領用、移位與銷貨被阻擋並提示盤點單號；盤點結束或中止後凍結自動解除。
- 主管可對單張被阻擋的單據放行，放行者與原因寫入稽核軌跡。
- 送單者與核准者不得為同一人。
- 差異率超過門檻（預設 1%，可調整）時，核准時必須附帶盤點原因說明；v1 不設金額門檻（v1 不計算成本，無金額基準）。[ASSUMPTION: 盤點差異僅設差異率門檻（預設 1%），不設金額門檻——v1 無成本引擎，金額門檻無基準]
- 核准後自動產生庫存調整並更新可用庫存，且核准與放行皆寫入稽核軌跡。
- 手動庫存調整亦須經主管核准後才影響可用庫存，並記錄原因碼（例如盤盈、盤虧、損壞、誤錄）；未經核准不影響可用庫存。

### 4.6 採購與安全水位

**描述：** 依商品安全水位自動找出需補貨的品項，產生補貨建議並建立採購單，走送單與核准流程；核准後的採購單是倉管收貨的依據。

**功能需求：**

#### FR-16: 安全水位與補貨建議清單
[採購或主管] 可以 依商品或商品類別設定安全水位與補貨倍數；[採購人員] 可以 查看所有低於安全水位的商品清單。

**可測試結果：**
- 商品個別設定優先於類別設定。
- 安全水位以全公司可用庫存合計為比較基準（v1 不做分倉水位，避免與商品層水位量綱不一致）。[ASSUMPTION: 安全水位僅依商品或商品類別設定，不做分倉水位]
- 清單只顯示可用庫存低於安全水位的品項。
- 建議採購量 = 安全水位 × 補貨倍數 − 可用庫存，最小值為 1。
- 清單可依商品類別篩選。
- 清單可勾選品項直接帶入採購單草稿。
- 安全水位設定變更記錄於稽核軌跡。

#### FR-17: 建立採購單
[採購人員] 可以 建立採購單，選擇供應商、品項、數量、單價與預估交期。

**可測試結果：**
- 採購單總價 = Σ(數量 × 單價)，四捨五入至小數 2 位。
- 預估交期必填，格式為日期。
- 採購單可從補貨建議清單一鍵帶入後再調整。
- 同一供應商商品可在一張採購單內合併多個品項。

#### FR-18: 採購單送單與核准
[採購人員] 可以 送交採購單；[主管] 可以 核准或駁回。

**可測試結果：**
- 草稿 → 待核准 → 已核准／已駁回，狀態不可跳階。
- 已核准採購單的內容不可修改（見 FR-20）。
- 核准者不可為送單者本人（需第二人覆核）；種子資料須提供至少兩名主管帳號以示範此流程。
- 核准時自動指派採購批次流水號（格式 `PO-YYYYMMDD-序號`，序號於當日遞增），並記錄帶入日期（核准日）與總價。
- 採購單可依供應商、日期、狀態查詢。

### 4.7 銷貨（最小可用）

**描述：** 銷售端只做「能把賣掉的商品記成一張單並讓庫存自動扣減」這一件事。

**功能需求：**

#### FR-19: 銷貨單與庫存扣減
[主管] 可以 建立銷貨單，記錄品項、數量、單價、銷貨人與日期，並在送出時扣減庫存。

**可測試結果：**
- 成交金額 = Σ(數量 × 單價)，四捨五入至小數 2 位。
- 銷貨人自動帶入目前使用者與今天，可修改。
- 送出時可用庫存不足則拒絕，並顯示各庫位可用庫存。
- 送出即產生庫存異動並更新可用庫存。[ASSUMPTION: v1 採「送出即扣減」，不做「先保留待核准」——最小可用下不需要賣出鎖定的複雜度]
- 銷貨單送出後不可修改，只能作廢重開。

### 4.8 單據流程

**描述：** 各類單據的生命週期不盡相同，但共享同一組原則：送單或送出後內容唯讀，只能作廢後重開新單。

**功能需求：**

#### FR-20: 各單據狀態流轉與作廢重開
[系統] 可以 管理五類單據的狀態流轉；[有權限的使用者] 可以 作廢已送出的單據並重開一張新單。

**可測試結果：**
- 各單據的合法狀態與轉移如下，不可跳階、不可逆向：

  | 單據 | 狀態流轉 |
  | --- | --- |
  | 採購單 | 草稿 → 待核准 → 已核准／已駁回；已核准 → 已作廢 |
  | 進貨單 | 草稿 → 已送出；已送出 → 已作廢 |
  | 銷貨單 | 草稿 → 已送出；已送出 → 已作廢 |
  | 盤點單 | 進行中 → 已提交 → 已核准；進行中 → 已中止；已提交 → 已作廢；已核准 → 已作廢 |
  | 庫存調整 | 草稿 → 待核准 → 已核准／已駁回；已核准 → 已作廢 |

- 進貨單與銷貨單送出即生效，不設核准關卡；有核准關卡者只有採購單、盤點單與庫存調整。
- 由盤點核准自動產生的庫存調整直接進入「已核准」，不再走一次送單與核准；手動申請的庫存調整則從「草稿」開始（見 FR-15）。
- 送單或送出後內容唯讀；每次狀態轉換寫入稽核軌跡。
- 已作廢單據保留完整內容且不可刪除；重開的新單以欄位引用原單號，可由新單反查原單。
- 作廢銷貨單、進貨單或已核准的庫存調整時，以反向的結存明細沖銷原異動，恢復可用庫存；盤點單作廢則不產生任何沖銷（盤點本身不改變庫存）。沖銷一律以新增反向明細達成，不刪除或修改既有結存明細。

### 4.9 查詢、稽核與 API

**描述：** 提供足以支撐倉管與採購日常的查詢、稽核查閱與 REST API。

**功能需求：**

#### FR-21: 庫存查詢與進銷存彙總
[使用者] 可以 依商品條碼、商品編號或名稱查詢各庫位現存數量、可用庫存、批號、批次數量與最近異動時間；並可查看期間內各商品的進貨、領用、銷貨與調整彙總。

**可測試結果：**
- 查詢支援以條碼、編號、部分名稱查詢。
- 結果顯示庫位、現存數量、可用庫存、批號與批次數量。
- 彙總數量與逐筆異動加總一致；可依日期區間與商品類別篩選。

#### FR-22: 不可竄改的稽核軌跡
[系統] 可以 為所有敏感操作寫入不可竄改的稽核紀錄；[主管] 可以 依使用者、物件類型、日期範圍查詢稽核紀錄。

**可測試結果：**
- 敏感操作包含：角色指派、安全水位設定、庫存調整、盤點核准、單據送單／核准／作廢、負庫存放行、盤點凍結放行、登入與登出。
- 稽核紀錄僅能新增，沒有任何介面或 API 可修改或刪除。
- 每筆紀錄含操作者、時點、物件類型、物件編號、欄位異動前值與後值。
- 記錄具先後序號，可檢查是否有連續性缺口（竄改偵測）；進階做法是以雜湊鏈串接內容以檢查欄位值是否遭改動（實作選項，見 addendum §1.9）。
- 稽核紀錄不得被一般使用者查閱。

#### FR-23: REST API 與 OpenAPI 文件
[開發者] 可以 透過 REST API 讀寫商品、庫存與單據，並查閱自動產生的 OpenAPI 文件。

**可測試結果：**
- API 以 JSON 傳輸，需附帶有效 token，無憑證或憑證失效回應 401。
- 提供 Swagger／OpenAPI 描述文件，含每個端點的請求與回應範例。
- 非授權角色呼叫對應端點回應 403。
- API 與網頁介面共用同一套領域規則，不存在僅在 API 可達的庫存寫入路徑。

## 5. 跨域非功能需求

- **資料量級（教學示範規模）** — 種子資料預設 200 筆商品、1 個倉庫、30 個庫位、15 個供應商、約 150 筆庫存異動，足以示範全部流程。[ASSUMPTION: 教學版本以單機示範規模為主，不以企業級資料量為目標]
- **效能** — 庫存與商品查詢在上述規模下，單筆查詢回應 P95 ≤ 1 秒；頁面首次載入 ≤ 2 秒。
- **可用性** — 教學環境以單機部署為主；服務重啟後資料不遺失；每日自動備份資料庫，且備份須可還原驗證。[ASSUMPTION: 教學版不要求 99.9% 可用性與災備演練]
- **資安** — 密碼以不可逆雜湊儲存；API 以 token 認證；應用程式以專用資料庫帳號連線且僅授予必要權限；連線字串僅存於環境變數，不寫入程式碼；本機練習用的環境手冊含明文密碼，須排除於版本控制之外。
- **稽核不可竄改** — 稽核紀錄僅追加、具序號，支援完整性檢查。
- **可維護性（教學導向）** — schema 以版本化遷移腳本管理，程式碼分層清楚，提供種子資料重置指令，讓學生能在課堂上重現環境。[ASSUMPTION: 資料庫使用本機既有 PostgreSQL 18.6 環境 `Ailearn`（名稱大小寫敏感），schema 由 v1 從零設計]
- **可及性** — 主要操作流程可完全以鍵盤完成；表格與表單具備可讀標籤。

## 6. 資料完整性與業務規則約束

*本節是本產品的核心關切：庫存數字一旦不可信，整套系統的價值歸零。以下為硬性約束，不可在實作階段自行放寬。*

- **單一寫入入口** — 任何庫存數量的變動只能經由同一套領域規則產生；網頁介面與 REST API 走同一條路徑。禁止任何畫面直接修改「庫存數量」欄位。[ASSUMPTION: 採單一寫入入口，不以 Trigger 或前端彙算達成]
- **結存明細不可變** — 結存明細僅能追加，不可 UPDATE 不可 DELETE；更正一律以反向明細沖銷達成。
- **負庫存預設禁止** — 出庫前檢查可用庫存，不足則拒絕；僅主管可放行，放行者與原因必須寫入單據與稽核軌跡。允許負庫存會讓盤點差異與稽核失去意義。[ASSUMPTION: 預設禁止負庫存，主管放行需填原因並留稽核紀錄]
- **不可用完再改** — 已送單或已核准的單據內容唯讀；更正只能作廢重開，新單引用原單號。
- **第二人覆核** — 送單者與核准者不得為同一人（採購單、盤點差異、庫存調整皆適用），因此種子資料至少提供兩名主管帳號。
- **可用庫存定義** — v1 沒有任何預留／保留機制，可用庫存 = 現存數量；未來若加入訂單預留，需同時擴充資料模型與本節約束。
- **盤點凍結優先** — 盤點期間範圍內異動一律阻擋，除非主管針對單張單據放行。
- **成本不外洩** — 採購單價與批次進貨單價對倉管角色遮蔽，且遮蔽在 API 序列化層完成。
- **單位一致** — 庫存數量一律以商品基本單位儲存；換算只在輸入與顯示層發生。
- **併發一致性** — 多名使用者同時操作同一商品同一庫位時，寫入採樂觀鎖；版本衝突時回應 409 並要求重試，不得以最後寫入覆蓋。[ASSUMPTION: 採樂觀鎖，衝突回應 409]

## 7. 非目標（明確排除）

- 我們不做生產排程與物料需求計算（BOM／MRP），v1 只做庫存與採購。
- 我們不做毛利分析、毛利率報表、定價建議與建議售價，v1 的銷售只做記錄與扣減。
- 我們不做銷售折扣規則、組合商品與銷貨退貨。
- 我們不做跨倉庫調撥與在途庫存，v1 只有一個倉庫。
- 我們不設會計角色，不做會計分錄、稅務申報與電子發票開立。
- 我們不做條碼標籤排版與列印，v1 只讀取條碼。
- 我們不做序號（單件商品）管理，只做批號追蹤。
- 我們不做 POS 收銀機、電商商城與金流整合。
- 我們不做多公司、多租戶、多幣別與匯率換算。
- 我們不做行動裝置原生 App、離線暫存與盤點衝突偵測。
- 我們不做 CSV 匯入匯出、儀表板與圖表化報表（v1 以螢幕查詢與種子指令交付）。
- 我們不追求企業級的可用性、災備與合規認證。

> **[NOTE FOR PM] 課題簡報與本節的落差**：簡報第 12 頁明列五項能力——「快速搭配多項商品」、「給出折扣（可設定）」、「自動計算毛利」、「設定建議售價與預計毛利」，以及「發現其他倉庫有貨時打調貨單」。本 PRD 依「聚焦倉管＋採購端、銷售最小可用、只交最小可運作成果」的範圍決定，把這五項全部移出 v1。**若課程評分要求涵蓋簡報第 12 頁，需回填**：毛利與定價（擴充 FR-19、定價與折扣資料表、毛利報表）、組合商品（新增成分品項拆解）、跨倉調撥（新增調撥單與在途機制）——三者會顯著增加資料模型複雜度與工時，與「最小可運作」直接牴觸。此取捨需由授課教師確認。

## 8. v1 範圍

### 8.1 v1 包含（23 條功能需求，全部必做）

- 安全水位、補貨建議、採購單與核准（FR-16～FR-18）
- 銷貨單與庫存扣減（FR-19）

## 9. 成功指標

**主要**
- **SM-1**：一條端到端示範劇本可由授課教師在 15 分鐘內不重啟服務地完成：補貨建議 → 採購單 → 送單核准 → 進貨入庫 → 庫存查詢 → 銷貨單 → 盤點 → 差異核准。對應 FR-9、FR-11、FR-15、FR-16、FR-17、FR-18、FR-19、FR-21。
- **SM-2**：23 條功能需求在期末前 100% 可被驗收者逐條觸發，且結果符合其「可測試結果」。對應 FR-1～FR-23。
- **SM-3**：任一庫存數字都能由結存明細逐筆加總還原，盤點差異可 100% 追溯到單據與操作者。對應 FR-13、FR-15、FR-22。
- **SM-4**：課堂上任何時刻可一鍵重置種子資料回到可示範狀態，重置執行時間 ≤ 30 秒。

**次要**
- **SM-5**：評審者能依 PRD 第 4 節獨立驗證至少 80% 的功能需求，無需閱讀程式碼即可操作。對應 FR-1～FR-23。
- **SM-6**：學生能依 `addendum.md` 的資料表草案與 OpenAPI 文件各自完成一個模組的擴充。對應 FR-23。

**反向指標（不應為了達標而追求）**
- **SM-C1**：功能數量 — 不以「功能越多越好」為目標。23 條功能需求已足以支撐 SM-1 的示範劇本；若時間不足，應先砍第 8.2 節的 v2 清單，而不是讓 v1 的每一條都做到一半。
- **SM-C2**：稽核範圍 — 不以犧牲操作便利性換取更嚴格的稽核（例如要求每個查詢都寫稽核），稽核範圍限於 FR-22 列舉的敏感操作。
- **SM-C3**：資料量 — 不以灌入大量種子資料製造「看起來很完整」的假象；維持能在一堂課內示範的規模。

## 10. 開放問題

1. 簡報第 12 頁的毛利、折扣、組合商品、建議售價與調貨單是否要回填 v1？（見第 7 節 [NOTE FOR PM]）這會直接改變範圍與工時。
2. 採購單的「帶入日期」以核准日或送出日為準？目前預設核准日（FR-18）。
3. 安全水位的補貨倍數是全公司統一或依商品類別設定？目前預設依商品類別（FR-16）。
4. 盤點差異率的核准門檻預設值？目前假設 1%（FR-15）。
5. 是否有「最小起訂量（MOQ）」或最小包裝單位需要強制？目前僅記錄於供應商報價，不強制（FR-7）。
6. API 是否只供課堂內部使用，還是需對外開放 Swagger UI？目前假設僅內網可存取。[ASSUMPTION: API 僅供課堂內網使用，不對外公開 Swagger UI]
7. 課程評分對「文件產出」的要求為何？目前假設最小可運作成果不要求完整架構文件包。[ASSUMPTION: 以最小可運作成果為交付標準，不要求完整架構文件包]
8. 主管角色是否需要拆成「倉管主管」與「採購主管」以示範二級覆核？目前單一主管角色，差異率超標只加註說明。
9. 期初庫存與安全水位的初始值由誰提供（授課教師指定或種子腳本自訂）？目前假設由種子腳本自訂並在課程前可調整。[ASSUMPTION: 期初庫存與安全水位初始值由種子腳本自訂]
