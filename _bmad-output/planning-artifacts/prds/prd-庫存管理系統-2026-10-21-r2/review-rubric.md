# PRD Quality Review — 庫存管理系統（倉管與採購端 · 教學示範版）r2

> 校準說明：本 PRD 為課程教學專題（交付＝最小可運作成果），第 5 節已明確拒絕 99.9% 可用性、災備演練與合規認證，第 7 節非目標清單具體。因此本審查**不**要求企業級治理、審計認證或正式風險登記簿；凡「可測試」皆以「一名學生開發者能依 PRD 寫出自動化測試或可重複的驗收步驟」為標準。

## Overall verdict

這份 PRD 的骨架相當紮實：37 條 FR 每條都帶有可測試結果、術語表與 ID 編號連續且交叉引用可解析、§7 非目標與 §9 的反向指標（SM-C1～C3）都是具體而非樣板的寫法——在一份課程 PRD 裡這已經高於常態。風險集中在兩處：其一，§4 的 FR 層存在成組的內部矛盾（FR-27 的單一狀態機與 FR-11／FR-16／FR-26 的實際生命週期衝突、FR-20 的「二級主管」在單一主管角色模型下不存在、「差異金額」在 v1 無成本引擎下不可計算），這些會讓不同學生做出分歧的實作；其二，最關鍵的決策段落 §7 `[NOTE FOR PM]` 關於「給了什麼」的盤點清單與 §4／§8.1 不符（跨倉調貨單並未被移到非目標，FR-16 有實作），加上 37 條 FR 未分必做／選做，這正是 7 堂課交付時最容易爆掉的地方。

## Decision-readiness — adequate

PRD 有真正的決策姿態，不是「什麼都平衡一下」：§7 的 `[NOTE FOR PM]` 精準指向課題簡報第 12 頁與本 PRD 範圍的落差，並給出回填條件與影響面；§10 的 8 個開放問題多數附帶「目前假設」而非空問；`addendum.md` §1.5／§1.6／§4 把取捨寫成「優點／代價」與「為何排除」兩欄，而非中性描述。這比多數 PRD 誠實。

問題出在最重要的一段。§7 的註記宣稱課題簡報第 12 頁列出的五項——「自動計算毛利、設定折扣、快速搭配多項商品、設定建議售價與預計毛利、跨倉調貨單」——「本 PRD …決定把這些移到非目標」。但 FR-16 跨倉調撥與在途庫存、UJ-4 倉管小陳跨倉調撥都在 v1 範圍內（§8.1 明列 FR-14～FR-16）。決策者若只讀這一段，會誤以為跨倉調貨單也已被放棄、或誤以為要補回它是額外成本。這一段的用途正是讓人權衡「課程評分 vs 範圍」，而它的清單是錯的。此外 §10 OQ3（補貨倍數是全公司統一或依商品類別？）其實已被 FR-21 決定（依商品、類別或倉庫），OQ1 也沒有決策者與截止日期。

### Findings
- **[high]** §7 `[NOTE FOR PM]` 的「給了什麼」清單與 §4／§8.1 不符 — 註記把「跨倉調貨單」一併列入被移至非目標的項目，但 FR-16（跨倉調撥與在途庫存）與 UJ-4 都實作了它，§8.1 亦明列 FR-14～FR-16 在 v1 內。整份 PRD 唯一的範圍決策段落帶著一份錯誤的盤點清單；決策者據此判斷「簡報第 12 頁要補回什麼、要付出什麼」會得到錯誤基準。*Fix:* 改寫為只列真正被捨棄的四項（毛利／折扣／組合商品／建議售價），明寫「跨倉調貨單保留於 v1（FR-16）」，並把 `addendum.md` §1.5 的代價（批次單價不會攤平，日後算真實毛利需補 `cost_layers`）與估時一起寫進去，另指定決策者與截止日。
- **[medium]** §10 開放問題的成熟度不一致 — OQ1（毛利是否回填）缺「誰決定、何時決定」；OQ3（補貨倍數統一或依類別）其實已由 FR-21 決定為三層（商品／類別／倉庫），卻仍列為未決。兩者都讓 §10 看起來比實際更開放或更封閉。*Fix:* OQ1 補上決策者與日期（例如「課程方於第 1 堂前確認」）；OQ3 改寫成真正未決的部分：「商品、類別、倉庫三層同時命中時的優先序（商品 > 類別 > 倉庫）目前未定義」。

## Substance over theater — strong

沒有一處是為了充滿模板而寫的。角色不是裝飾：倉管（UJ-1／2／4／5、FR-11～19）、採購（UJ-3、FR-9／21～24）、主管（FR-2／7／10／18／20／24／29／31／34／35）、銷售（UJ-6、FR-26）各自驅動具體需求；「授課教師（次要使用者）」雖 unusual，卻是這份交付物真正的需求方，並在 SM-1／SM-4／SM-6 與 §5「種子資料重置指令」中落實。PRD 沒有「創新」段落，`addendum.md` §1.4 的「同一套系統內並存 MVC 與 MVVM」是可辯護的教學主張而非虛構的差異化。§1 願景綁定「對倉管人員而言，它取代的是白板、便當紙與 Excel；對採購而言，它取代的是對著舊對帳表猜數量」，換成同類別其他 PRD 會立刻不合身，不算願景樣板。本維度無需提出修正。

## Strategic coherence — adequate

PRD 有一條明確主線，而且 §6 把它挑明了：「本節是本產品的核心關切：庫存數字一旦不可信，整套系統的價值歸零」。§1 的雙主線（東西在哪／該補多少）與 §6 的硬約束（單一寫入入口、結存明細不可變、第二人覆核）互相咬合，FR 的分組（主檔→異動→盤點→採購→查詢→匯入導出）也沿著主線而非「好做先做」排列。SM-3（任一庫存數字都能由結存明細逐筆加總還原）是真正驗證主線的指標。

反向指標是這份 PRD 的亮點：SM-C1 拒絕不支撐示範劇本的新功能、SM-C2 明講不以稽核換取便利且把稽核範圍釘在 §4.10、SM-C3 反對灌資料製造完整假象——這三條都是具體的、可被違反的，而不是裝飾。

問題出在 SM 與 FR 的對應，以及 SM 的層級混雜。SM-1 的「對應 FR-」清單與它自己的劇本內容不一致（多列 FR-14 領用、少列 FR-20 差異核准、FR-23 建立採購單、FR-33 彙總報表）；SM-4 對應 FR-35，但 FR-35 是 CSV／Excel 匯入，「一鍵重置種子資料」根本不是 FR-35 的能力（它只出現在 §5 維護性與 `addendum.md` §5 的 `flask seed --reset`）；SM-2「37 條功能需求皆具備可測試結果」與 SM-5「評審者能依 PRD 第 4 節獨立驗證至少 80%」量的是**文件品質**，不是產品或教學成果。

### Findings
- **[medium]** §9 SM-1 的 FR 對應與劇本內容雙向不符 — SM-1 的劇本是「補貨建議 → 採購單 → 核准 → 進貨入庫 → 庫存查詢 → 銷貨單 → 盤點 → 差異核准 → 調撥 → 彙總報表」，但「對應 FR-」只列 FR-11、FR-14、FR-16、FR-19、FR-22、FR-24、FR-26：FR-14（領用）不在劇本裡，而 FR-20（差異核准）、FR-23（建立採購單）、FR-32（庫存查詢）、FR-33（彙總報表）明明在劇本裡卻漏列。下游故事若照著 FR 清單抽，會漏做劇本步驟或多做不在劇本的領用。*Fix:* 依劇本逐步列出對應 FR，或明寫「領用不在本劇本中，屬於另一條示範線」。
- **[medium]** SM-2／SM-5 是文件品質指標混入產品指標，SM-4 對應錯誤 — 「37 條功能需求皆具備可測試結果，且每條在系統中可被實際觸發」衡量的是 PRD 寫得好不好，不是系統好不好；「評審者能依 PRD 第 4 節獨立驗證至少 80% 的功能需求，無需閱讀程式碼」既無測量方法（誰驗、怎麼算通過），也把驗收門檻訂在 80%（暗示 20% 不必被驗證，與 SM-2「37 條皆可觸發」互相矛盾）；SM-4「一鍵重置種子資料，重置 ≤ 30 秒。對應 FR-35」則對錯了 FR，FR-35 沒有任何重置能力。*Fix:* SM-2 改為系統行為指標（例如「示範劇本每次重跑後庫存數字一致」）；SM-5 明確驗證方法與分母（例如「評審者依 §4 逐條走查，37 條全部可在無原始碼下完成」）；SM-4 改對應到新增的 FR-38（種子重置）或 §5 維護性條目。

## Done-ness clarity — adequate

形式上這是本 PRD 最強的一節：37 條 FR 全部有 2～5 條「可測試結果」，無一條使用「合理」「友善」「妥善處理」這類形容詞；FR-6／FR-19／FR-22／FR-23／FR-26 給出了明確公式（四捨五入位數、Σ 差異率、建議採購量、總價、成交金額），FR-1／FR-20／FR-34 給出了預設值，FR-3／FR-36 把欄位遮蔽一路寫到 API 序列化層與匯出檔，FR-37 給出 401／403 的具體狀態碼。以教學交付的標準而言，這已經是「工程師讀完就知道 done 是什麼」的水準。

但「可測試結果」不等於「可實作且互不矛盾」，而這一節的問題恰恰在此，且集中在審核與單據生命週期這條主軸上：FR-27 規定所有單據共用「草稿 → 待核准 → 已核准」狀態機，但 FR-11 進貨單「送出即寫入庫存異動」、FR-16 調撥單走「建立 → 標記出貨 → 確認收貨」、FR-26 銷貨單的 `[ASSUMPTION]` 更明說「v1 採『送出即扣減』，不做『先保留待核准』」——三者的實際生命週期都沒有「待核准」這一段。此外 FR-20 的「二級主管」在 §4.1 的四角色模型（倉管／採購／銷售／主管）下沒有對應角色（§10 OQ8 明寫「目前單一主管角色」），而「差異金額超過門檻」在 v1 不實作成本引擎（`addendum.md` §1.5 明寫「v1 不計算」移動平均或 FIFO」）的前提下根本無從計算。

### Findings
- **[high]** FR-27 的單一狀態機與 FR-11／FR-16／FR-26 的實際生命週期衝突 — FR-27 宣告「狀態僅能依序流轉：草稿 → 待核准 → 已核准」，且其對象明列「採購單、進貨單、銷貨單、調撥單、盤點單與庫存調整」；但 FR-11「進貨單送出即寫入庫存異動」若仍需待核准，庫存會在核准前就動；FR-16 調撥單走出貨／到貨兩段；FR-26 的 `[ASSUMPTION: v1 採「送出即扣減」，不做「先保留待核准」]` 直接排除了「待核准」狀態。同一份 PRD 對「銷貨單有無待核准」給出兩個互斥答案，故事拆解會在此分岔。*Fix:* 以一張 per-document 狀態表取代 FR-27 的通則（例：銷貨單＝草稿→已送出→已作廢；進貨單＝草稿→已入庫→已作廢；採購單＝草稿→待核准→已核准／已駁回→已作廢；盤點單＝進行中→待核准→已核准），並讓 FR-27 只負責「每種狀態轉換都寫稽核、核准後唯讀」這兩條共通規則。
- **[high]** FR-20 的兩項門檻在現有模型下不可執行 — 「差異率超過門檻（預設 1%）或差異金額超過門檻時，需二級主管核准」：其一，§4.1 的角色只有倉管／採購／銷售／主管四種，全文「二級主管」只此一處出現且無定義，§10 OQ8 更確認「目前單一主管角色」；其二，「差異金額」需要成本估值，而 `addendum.md` §1.5 明確「v1 不實作移動平均或 FIFO 成本引擎，只記錄批次進貨單價作為成本快照」——沒有攤平規則就沒有金額，FR-20 的第一條可測試結果因此無法實作也無法驗證，而它是 UJ-2 與 §6「第二人覆核」的控制點。*Fix:* 二選一——(a) 明確定義二級審核（新增「區／倉主管」角色或改為「主管 + 另一個持有核准權限的帳號」），並把門檻觸發改為純差異率；(b) 保留金額門檻，但補上估值規則（例如「以盤點範圍內批次的最新進貨單價加權平均估值，僅作門檻判斷用，不做成本結轉」）。
- **[medium]** FR-12 指向 v1 不存在的功能 — 「該類進貨在採購金額統計中可被篩選區分」要求一個「採購金額統計」，但 §4.11 的三個查詢報表是庫存查詢（FR-32）、進銷存彙總（FR-33，僅數量）、呆滯品清單（FR-34），全 PRD 沒有任何金額報表，§8.1 也未列入。*Fix:* 改寫為「該類進貨在進銷存彙總中可依來源篩選區分（FR-33）」，或把「採購金額統計」正式列為 v1 需求與 FR。
- **[medium]** FR-2 的「調整角色的功能權限」與 §4.1 的固定角色制假設邊界不明 — §4.1 的 `[ASSUMPTION: 採固定角色制 …不建自訂授權規則引擎]`，但 FR-2 允許主管「調整角色的功能權限」；這兩者是硬編碼映射與資料驅動權限表兩種不同模型。`addendum.md` §2.1 已有 `role_permissions(role_id, permission_code)` 表，實際偏向後者。邊界不清會讓學生各自選一種，FR-2 的「採購帳號看不到盤點建立入口」測試也會在兩種模型下有不同解讀。*Fix:* 明寫二選一（例如「固定角色 + 唯讀權限表，權限由種子資料決定、不提供編輯 UI」或「主管可編輯 role_permissions，但僅限既有權限碼的開關」），並讓 FR-2 的可測試結果對應到該選擇。
- **[medium]** FR-35 的重複判定鍵與 FR-4 的商品編號規則衝突 — FR-35 說「重複資料以商品編號判斷，可選擇跳過或覆寫」，但 FR-4 說「商品編號唯一且自動遞增，建立後不可修改」，「商品編號」不可能同時是自動產生又由匯入檔帶入比對。另外 FR-35 的匯入對象寫成「商品、供應商、期初庫存與安全水位等初始資料」，「等」讓範圍開放；FR-35 也未說明匯入的期初庫存如何產生合法的庫存異動與結存明細（直接改 on_hand 會違反 §6「單一寫入入口」）。*Fix:* 改以「商品條碼」或「外部商品代碼（自訂欄位）」作為重複判定鍵；期初庫存匯入明定「必須產生一筆 movement_type=期初 的結存明細」，並列出完整匯入對象清單。
- **[medium]** FR-14 與 FR-26 構成兩條銷售出庫路徑，報表歸屬不明 — FR-14 允許「[倉管或銷售人員] 領用庫存並指定用途（銷貨、客戶寄貨、內部損耗）」，術語表也把「銷貨」列為領用用途之一；但 FR-26 另有銷貨單（記單價、成交金額、銷貨人）。當銷售人員在 FR-14 選擇用途「銷貨」時，不會產生銷貨單，FR-33 的進銷存彙總該如何計（銷貨一項？領用一項？兩邊都不算？）沒有答案，也讓銷售可以繞過單據流程直接扣減庫存。*Fix:* 明定銷貨只能走 FR-26；FR-14 的用途清單移除「銷貨」（或改為「領用一律視為非銷售用途，銷貨請建立銷貨單」）。
- **[medium]** FR-21／FR-22 的安全水位層級與預設值不足以定出建議採購量 — FR-21 說可「依商品、商品類別或倉庫設定」，但可測試結果只測「商品個別設定優先於類別設定」，倉庫層級的優先序、以及商品同時命中三層時取哪一層都未定義；術語表又只把安全水位定義為「商品低於此數量…」，與倉庫層級互相矛盾。FR-22 的「建議採購量 = 安全水位 × 補貨倍數 − 可用庫存」在兩者都未設定（無預設值）時無法定值，而 `addendum.md` §5 又假設有 12 筆低於安全水位可示範 FR-22。*Fix:* 補一條三層優先序（商品 > 類別 > 倉庫）與未設定時的預設（例：安全水位 0、補貨倍數 1，或「未設定不列入補貨建議」），並讓 FR-22 說明用的是哪一層水位與哪個範圍的可用庫存。
- **[medium]** FR-33 的彙總類別缺「移位」，與其自身的一致性檢核互斥 — FR-33 只彙總「進貨、領用、銷貨、調整與調撥」五類，但 FR-15 明寫「移位記錄於庫存異動，異動類型為移位」；於是 FR-33 的第一條可測試結果「彙總數量與逐筆異動加總一致」在存在移位紀錄時必然失敗。調撥本身在結存明細裡是調出、調入兩筆，歸類規則也未寫。*Fix:* 明列移位（以及無單據入庫）為彙總類別，或把第一條結果改為「各類別彙總與該類別逐筆加總一致（移位類別單列且不影響倉庫總量）」。
- **[low]** 三處「可測試結果」仍是形容詞或循環敘述 — FR-8「電話格式驗證通過，支援多筆聯觸人電話」未定義電話格式，無法判定通過；FR-16「在途數量在畫面上以不同視覺標示，避免被誤判為可用貨」未給判準；FR-19 的「差異率 = Σ|實盤 − 帳面| ÷ Σ帳面」在 Σ帳面 = 0 時未定義。*Fix:* 給出格式規則（例如「允許 0X-XXXXXXX、0XXX-XXX-XXX、09XX-XXX-XXX，純數字視為無效」）、視覺判準（例如「在途數量列固定顯示『在途』標籤且預設排序在可用庫存之後」）、以及除零時差異率定義為 0。
- **[low]** §5 跨域非功能需求三處缺量測判準 — 「每日自動備份資料庫」沒有還原驗證要求（備份不可還原等於沒有備份）；「主要操作流程可完全以鍵盤完成；表格與表單具備可讀標籤」沒有引用任何標準或列出「主要操作流程」的範圍；「單筆查詢回應 P95 ≤ 1 秒」沒有說明樣本數、資料量與量測工具。*Fix:* 補「每週至少一次還原驗證且還原後種子資料一致」、把可及性綁到具體流程清單與 WCAG 2.1 AA 的部分條款、效能指標補上量測方法（seed 300 筆、連續 100 次查詢、取 P95）。

## Scope honesty — adequate

這份 PRD 的範圍誠實度明顯高於常態：§7 有 10 條具體非目標（不是「不做複雜功能」這種空話）、§8.1／8.2／8.3 三層劃分（v1 包含／延後 v2／明確不做）、§10 OQ1 與 §7 註記連動、§5 與 §7 明確拒絕企業級治理、`addendum.md` §1.5 把放棄成本引擎的代價寫成具體句子（「批次單價不會被自動攤平到各批剩餘數量上，若日後要算真實毛利需補做成本層」）。開放項目密度（8 個開放問題＋11 處 inline `[ASSUMPTION]`＋1 個 `[NOTE FOR PM]`）對一份教學型 PRD 完全適宜，不是綠燈_build 前的阻塞。

缺口在 §4 承諾與 §7／§8 宣告範圍之間有兩處沒對齊，以及 §8.1 沒有分級。§2.2 非使用者把「決策者對…呆滯資金占用的深度需求」列為 v1 排除，但 FR-34 呆滯品清單就在 v1 內（§8.1 明列 FR-32～FR-34），對象正是採購或主管。§8.1 把 37 條 FR 全部列為 v1 等價，沒有「必做／選做」分級，而 `addendum.md` §8 的風險緩解卻寫「批次與雜湊鏈列為選作加分項」——這兩份文件對同一件事的承諾強度不一致（PRD 端 FR-5 把批次管理列為硬需求，addendum 端說批次可以不做）。

### Findings
- **[medium]** §8.1 的 v1 沒有承諾強度分級，且與 SM-C1 自我矛盾 — 37 條 FR 全數列為 v1 等價交付，沒有任何一條被標記為可延後的選作（FR-29 單號規則、FR-34 呆滯品清單、FR-6 單位換算、FR-9 報價生效期間都不在 SM-1 的示範劇本上，也不支撐 §1／§6 的主線），但 §9 的反向指標 SM-C1 明寫「新增功能若不支撐 SM-1 的示範劇本，應拒絕」——反增量規則只對未來生效，v1 自身卻未通過這把尺子。`addendum.md` §8 更直接把「批次、盤點凍結、稽核雜湊鏈」列為「選作加分項」，與 PRD 端 FR-5／FR-18／FR-30 的硬需求敘述不一致。以 addendum §6 的 7 堂課排程計，37 條 FR 全部做完是最主要的交付風險，而 PRD 沒有任何機制把風險攤出來。*Fix:* 在 §8.1 為每組 FR 加上「必做／選做」標記（例如必做＝FR-1～5、10～16、17～20、21～26、30、35；選做＝FR-6、29、31、34、37），並讓 SM-C1 改寫為「v1 內亦以此尺子複驗，選做項若時間不足可整組移除而不破壞 SM-1」。
- **[medium]** §2.2 非使用者與 §4.11／§8.1 對「呆滯」自相矛盾 — §2.2 把「決策者對『毛利分析、定價建議、呆滯資金占用』的深度需求」列為 v1 非使用者／排除項，但 FR-34「呆滯品清單」就在 v1 內且交付對象正是「[採購或主管]」。*Fix:* 從 §2.2 移除「呆滯資金占用」，或改寫為「不做呆滯資金的**金額占用**分析（僅提供天數清單，見 FR-34）」，與 §7／§8.2 的敘述對齊。
- **[low]** §7 非目標「不做…盤點衝突偵測」與 FR-17 已交付的「範圍重疊提示衝突」使用同名詞、不同意義 — §7／§8.2 指的是動態盤點的期中基準衝突（v2），FR-17 第三條是建立期範圍重疊檢查（v1）。讀者會誤以為 FR-17 違反非目標。*Fix:* 將 §7 該項改寫為「不做動態盤點的期中基準重算與衝突偵測」，並在 FR-17 補「建立期範圍重疊檢查」以對照。

## Downstream usability — adequate

工程素養這一段做得乾淨：術語表 40 條涵蓋了主檔、單據、庫存數量與流程用語；FR-1～FR-37、UJ-1～UJ-6、SM-1～SM-6 與 SM-C1～C3 編號連續、無重複、無跳號；13 處「Realizes UJ-N」全部指向存在的 UJ；FR-24 的「見 FR-27」、FR-32 的「第 5 節效能要求」、§8.1 的 FR 區間、SM 的「對應 FR-N」全部可解析；章節在抽出後大致能靠術語表自足（FR-13「結存明細」、FR-18「凍結範圍」等都在術語表覆蓋範圍內）。假設索引的 11 條 inline `[ASSUMPTION]` 也都在 §11 有對應條目。

### Findings
- **[medium]** UJ 覆蓋有兩個關鍵缺口：主管與授課教師 — 主管是覆核鏈的一端（FR-24「核准者不可為送單者本人」、FR-20 核准者與盤點者不得同一人、FR-18 放行、FR-31 稽核查詢），承擔十條 FR 卻沒有具名角色與旅程，「誰在什麼情境下按下核准」因此無從推導；授課教師是這份交付的實際需求方（§2.1 JTBD、SM-1／SM-4／SM-6、§5「提供種子資料重置指令」），同樣沒有 UJ。故事拆解時，這兩個角色最容易被做成通用 CRUD 頁面而不是情境驅動的流程。*Fix:* 補 UJ-7（主管小周在盤點差異超過門檻時的二級覆核，含 FR-20 的二級主管定義）與 UJ-8（授課教師小愛在課堂 15 分鐘內跑完 SM-1 劇本並重置資料，涵蓋 FR-35 重置）；或至少在 §2.1 為主管與教師各寫一條具名 JTBD 與對應 FR 清單。
- **[medium]** 未定義名詞散落於 FR 之中且被下游引用 — 「二級主管」（FR-20，全文僅此一處）、「具特權者」（FR-11「超收需具特權者放行」、§6「僅具特權者可放行」）、庫位「容量」（FR-10、術語表都未定義計量維度，而一個庫位會同時存放箱裝與罐裝商品）、「帶入日期」（FR-25、§10 OQ2，術語表未收錄）、「採購批次流水號」（術語表定義的 `PO-YYYYMMDD-序號` 實際就是採購單號，`addendum.md` §2.3 只有 `purchase_orders.po_no`，沒有「採購批次」這個實體，且與「批號」易混）、「確認紀錄」（FR-4 第三條）、FR-21 的倉庫層級安全水位（術語表只定義商品層級）。這些詞一進到故事與架構文件就會各自長出不同定義。*Fix:* 把「具特權者」「二級主管（或改寫後的審核級別）」「容量（以基本單位計，同商品基礎單位換算後合計）」與「帶入日期」補進術語表；「採購批次流水號」直接改稱「採購單號」以對齊 `po_no`；FR-4 的「確認紀錄」明確為「寫入稽核軌跡」。

## Shape fit — adequate

形式與產品相稱。這是多角色的內部後台（倉管／採購／主管／銷售，含 3 個倉庫、6 種單據），UJ 與具名角色在此不是負擔而是必要；§3 術語表與 §6 業務硬約束對一個強調「庫存數字要可信」的產品是承重構件；`addendum.md` 把「怎麼做」（技術選型、資料表草案、架構分層、被排除方案、種子資料、7 堂課開發順序）與 PRD 的「要做什麼」切開，這個分層安排是對的。形式沒有過度：沒有風險登記簿矩陣、沒有合規追溯矩陣、沒有企業級 NFR 儀表板，§5 與 §7 直接把「不追求 99.9% 可用性」「不追求企業級的可用性、災備與合規認證」寫成硬句。

唯一形狀上的不匹配是教學價值主張沒有對應的驗收標準：§1 第二段把「可被示範與可被檢驗」與「功能完整」並列，並舉出四個教學命題（分層架構的 MVVM/MVC 取捨、單一庫存異動引擎、關聯式資料庫建模、權限分層與稽核軌跡），但 §9 的 SM 只量「示範跑得完」（SM-1）、「需求可被驗證」（SM-2、SM-5）與「學生能擴充一個模組」（SM-6），沒有任何一條量「這堂課的架構命題講得清楚」。對課程交付物而言，這是形狀上缺的那一格。

### Findings
- **[low]** §1 的教學命題缺乏對應的 SM — 「它被設計成能用來講清楚分層架構（MVVM 與 MVC 的取捨）、單一庫存異動引擎的設計、關聯式資料庫建模、權限分層與稽核軌跡這些看得見的工程命題」列了四項教學目標，§9 沒有任何 SM 對應；`addendum.md` §1.4 的「同一套系統內並存兩種組織方式」其實是最有教學價值、也最該被驗收的一項，卻不在任何示範劇本內（SM-1 的十步驟沒有一步展示 MVC 與 MVVM 模組的差異）。*Fix:* 在 SM-1 的劇本加一步「同一支查詢在 MVC 模組（交易流程）與 MVVM 模組（查詢／盤點前端）的請求路徑對照」，或補一條 SM（如「學生能指出哪三個模組採 MVC、哪三個採 MVVM 並說出理由」）。
